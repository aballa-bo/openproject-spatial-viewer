# OpenProject Spatial Viewer

Project module for OpenProject that adds a **3D viewer** with **annotation**
tools that link to Work Packages.

Supported formats:

| Format | Status |
|---|---|
| glTF / GLB (mesh) | working (`THREE.GLTFLoader`) |
| glTF / GLB — Khronos `KHR_gaussian_splatting` | working as true per-splat rendering, decoded client-side (see *glTF Gaussian Splatting* below) |
| PLY / Gaussian Splatting (`.ply`, `.splat`, `.ksplat`) | 3DGS-trained files render as true per-splat Gaussians; a plain colored `.ply` falls back to a point cloud |
| Gaussian Splatting — PlayCanvas SOG (`.sog`) | working as true per-splat rendering, decoded client-side (see *SOG* below) |
| OBJ / Wavefront | working (`THREE.OBJLoader`) |
| IFC (BIM) | server-side `IfcConvert` → GLB, then rendered as GLB — see *IFC* |

Tested on OpenProject 16.6.

## Features

- WebGL viewer built on Three.js r128 (bundled in
  `app/assets/javascripts/openproject_spatial_viewer/vendor.bundle.js`).
- 3D markup tools: surface pin, polyline (points land exactly on the model
  surface), lasso, distance measurement. Sampling is screen-space and uses
  coalesced pointer events, so density is dense and scale-independent.
- **The lasso outline is a screen-space gesture while dragging** — the path is
  collected in canvas pixels and stroked on a 2D overlay canvas with
  `closePath()`, so it is dense and visibly closed *during* the drag.
- **The fill is built by raycasting, not by a shader.** `_buildLassoFill` lays
  a grid of sample points over the lasso polygon's screen-space bounding box
  (`pointInPolygon` keeps only the ones inside the drawn shape), casts one ray
  per sample at the model (BVH-accelerated), and triangulates the hit points
  into a real `THREE.Mesh` sitting exactly on the surface. Because every
  vertex IS a literal ray-surface hit, the fill cannot drift out of alignment
  the way a frozen-camera/depth-texture projection could — it is rebuilt fresh
  from whatever `this.camera` and `this.modelMeshObjects` are at call time, so
  it naturally spans every visible layer (mesh, IFC, point cloud) uniformly.
- It updates live while drawing (coarser grid, for snappy drag updates), gets
  one finer-quality rebuild at pointer-up, and is rebuilt again by
  `showAnnotationSurface()` -> `_selectSurfaceInLasso()` whenever a saved
  annotation is reopened (re-projecting its stored 3D ring through the
  current camera, then re-running the same raycast-grid fill).
- At pointer-up the screen ring is down-sampled to ≤220 points and projected
  to 3D for storage (`_screenPathToWorldRing`; rays that miss the mesh fall
  back to the focal plane) — 220 matches the resolution `_buildLassoFill`
  itself uses for the live fill, so the replayed selection matches the shape
  that was actually drawn instead of a coarser approximation of it.
- The free-hand polyline tool still raycasts per point, but with a hard budget
  of 8 rays per pointer event so a heavy mesh cannot stall the UI.
- `vendor/mesh-bvh.js` (three-mesh-bvh 0.5.23) accelerates those raycasts;
  trees are built once (`_ensureBVH`), and the library self-loads if the hook
  did not emit its `<script>`.
- The pointer is captured on stroke start, so a stroke that leaves the viewport
  does not end early.
- Annotations follow the **BCF** data model and are always tied to a Work
  Package — see *Annotations & BCF*.
- Section planes (X/Y/Z clipping), preset views (top/front/right/iso).
- The "Tickets & Annotations" button toggles the right panel open/closed
  (`toggleSidePanel`), and the panel is resizable by dragging its left edge —
  the width is clamped to 280–900 px and remembered in `localStorage`.
- Dedicated permissions: `view_spatial_models`, `manage_spatial_models`,
  `create_spatial_annotations`.

### `viewer_engine.js` fragments

The whole file lives inside a single `(function() { ... })()` closure (the
module-registration guard, the `SpatialViewerApp` constructor, and every
module-scope helper function all share that one scope), so the fragments
below are plain slices of it, not independent scripts -- `git diff`/editing
them individually is fine, but running any one of them alone is not
meaningful. `bin/build-viewer-engine.sh` concatenates them in this exact
order to produce `viewer_engine.js`; `install.sh` always runs it first.

```
engine/
  00_prelude.js            File header comment, IIFE open, registration guard
  05_geometry_utils.js     Small pure helpers with no DOM/scene dependency
                            (esc, point-in-polygon, pin orientation, lasso
                            grid triangulation)
  10_core.js               SpatialViewerApp constructor, Three.js init,
                            render loop, render settings, view fit/home
  20_layers.js             Multi-layer model loading orchestration: fetch
                            sequencing, fade in/out, the layer panel
  21_point_cloud_formats.js  load3DModel/_downloadModel (generic entry
                            point for every format) + raw binary parsing
                            for point-cloud/splat SOURCE formats (zip/PLY/
                            LAS/.sog)
  22_splat_rendering.js    Turns parsed point-cloud/splat data into THREE
                            objects: plain point clouds, and the true
                            Gaussian-splat renderers (SplatRenderer/
                            SplatRendererTex) -- this plugin's namesake
                            feature
  23_parsers.js            _parseModel (the format dispatcher) + mesh-
                            format parsing: zipped OBJ/glTF bundles, plain
                            glTF/GLB, IFC
  24_finalize.js           Post-load finalization (geometry sanitizing,
                            onModelLoaded) and the demo model
  30_interaction_lasso.js  pointer/keyboard/XR input, raycasting, lasso
                            drawing + fill, and the selection highlight (a
                            real 3D spotlight -- see _updateSelectionSpotlight)
  40_annotations.js        pin/measurement/snapshot creation, annotation
                            modal, side panel, save/update/delete, labels
  50_ui_vr_ar.js           toolbar wiring, VR, AR (calibration, pin/lasso
                            creation on site), tooltip/modal utils
  60_bootstrap.js          app lifecycle: boot/teardown, the Turbo Drive
                            navigation listeners, IIFE close
```

To regenerate `viewer_engine.js` locally (e.g. to run `node --check` on it
without doing a full `sudo bash install.sh`):

```bash
bash bin/build-viewer-engine.sh
```

All user-facing strings are English. `en.yml` is the fallback for every
locale; there is intentionally no per-language locale file.

## Installation

```bash
sudo bash install.sh
```

Copies the plugin to `/opt/openproject/modules/spatial_viewer`, adds it to
`Gemfile.modules`, runs `bundle install` and `db:migrate`, copies static assets
to `public/assets/openproject_spatial_viewer/`, checks for `IfcConvert`, and
restarts the services (`openproject-web-1` and `openproject-worker-1`).

### Quick redeploy of a single changed file

```bash
bash bin/build-viewer-engine.sh
sudo cp app/assets/javascripts/openproject_spatial_viewer/viewer_engine.js \
   /opt/openproject/modules/spatial_viewer/app/assets/javascripts/openproject_spatial_viewer/
sudo cp app/assets/javascripts/openproject_spatial_viewer/viewer_engine.js \
   /opt/openproject/public/assets/openproject_spatial_viewer/
sudo -u openproject bash -lc 'cd /opt/openproject && bundle exec rake tmp:cache:clear'
sudo systemctl restart openproject-web-1 openproject-worker-1
```

Then hard-reload the browser (Ctrl+Shift+R) so the new `viewer_engine.js` is
fetched instead of the cached copy. Note the deployed copy is unminified
with this shortcut (unlike a full `install.sh` run) -- fine for local
iteration, since it skips straight to `node --check`-clean source.

## "Download as .exe" (standalone Unity viewer)

The viewer toolbar has a "Download as .exe" button that packages a model
into a standalone Windows app: a **generic Unity player, built once** plus
that model's layer files and a manifest. The server never builds Unity
itself (this box has no Unity Editor, no Windows build tools, no GPU) — it
only zips together a player that's already built and this model's data.

- `app/services/spatial_viewer/unity_export_builder.rb` builds the zip:
  the player tree, `data/manifest.json` (mirrors `api_data`'s shape with
  local paths instead of URLs), the model's already-converted layer files,
  and a `config.json` whose `api_key` is **always blank** — the desktop app
  asks the end user for their own OpenProject personal API key on first run
  and keeps it only in local app data; it is never embedded in the download.
  All live sync from the desktop app (viewing/editing annotations and Work
  Packages) reuses this plugin's existing JSON endpoints over HTTP Basic
  auth (`apikey:<personal API key>`), the same mechanism OpenProject's own
  API v3 docs describe — no separate sync API exists.
- The Unity project source lives under `unity/SpatialViewerPlayer/` in this
  repo (not picked up by the gemspec, so it never bloats the packaged gem).
  Build it once in Unity Editor **on a machine that has Unity installed**
  (this server does not), producing output under
  `unity/SpatialViewerPlayer/dist/`.
- Run `sudo bash install.sh` again after that build — step 7/8 deploys
  `dist/` to `$ATTACHMENTS_STORAGE_PATH/unity_player/` (override with the
  `SPATIAL_VIEWER_UNITY_PLAYER_DIR` environment variable). Until a build is
  deployed there, the "Download as .exe" button stays hidden.
- This is the first of several planned milestones: full core rendering
  parity (point clouds, sections, render-quality panel), live annotation /
  Work Package sync, creating annotations from inside Unity, VR locomotion,
  and true Gaussian Splat rendering are not implemented yet.

## SOG (Gaussian Splatting)

`.sog` is PlayCanvas's "Spatially Ordered Gaussians" container — a zip of
`meta.json` plus a handful of lossless WebP textures, each pixel holding one
Gaussian's quantized data. Spec:
<https://developer.playcanvas.com/user-manual/gaussian-splatting/formats/sog/>.

- Decoded entirely client-side in `parseSOG`/`decodeWebpToImageData`
  (`viewer_engine.js`), reusing the same hand-rolled `unzipBuffer` already
  used for OBJ/MTL/glTF bundle uploads, plus the browser's native WebP
  decoder (`createImageBitmap` → canvas → `getImageData`).
- Position (`means_l`/`means_u`), scale + rotation (`scales`/`quats`), DC
  color + opacity (`sh0`) and, when present, degree-1/2 view-dependent color
  (`shN`, first 8 of up to 15 coefficients/channel) are all decoded and
  rendered as true per-splat elliptical Gaussians (`SplatRenderer`) — 3D→2D
  covariance projection with back-to-front depth sorting, not a colored
  point-cloud approximation. `.ply`/`.splat`/`.ksplat` 3DGS-trained files
  (detected via `scale_*`/`rot_*`/`f_dc_*`/`opacity` properties) go through
  the same renderer; a plain colored `.ply` with no Gaussian training data
  falls back to the point-cloud approximation used for LAS.
- `format === 'sog'` is checked before the generic zip-bundle sniff in
  `_parseModel`, since a `.sog` file is itself a zip and would otherwise be
  mistaken for an OBJ/glTF archive.
- Registered as its own format end-to-end: `SpatialLayer::FORMATS`/
  `KIND_BY_FORMAT` (auto-detected from the `.sog` extension for layers), the
  `model_format` dropdown option (for the legacy single-file model slot),
  and the `MODEL_CONTENT_TYPES`/`LAYER_CONTENT_TYPES` maps (served as
  `application/octet-stream`, same as the other binary formats). No
  server-side conversion step is involved — same as `.ply`/`.splat`.

## glTF Gaussian Splatting (`KHR_gaussian_splatting`)

A ratified Khronos glTF extension for storing 3D Gaussian splats directly in
a `.glb`/`.gltf` mesh primitive (a `POINTS`-mode primitive with `POSITION`
plus `KHR_gaussian_splatting:ROTATION`/`SCALE`/`OPACITY`/`SH_DEGREE_*`
attribute semantics). Spec:
<https://github.com/KhronosGroup/glTF/tree/main/extensions/2.0/Khronos/KHR_gaussian_splatting>.

- `THREE.GLTFLoader` (vendored here) has no idea this extension exists — it
  logs an "Unknown extension" warning and drops whatever that primitive
  described, which for a file that stores *all* its geometry this way means
  "parsed fine" but an empty, mesh-less scene. `_parseGltf` detects the
  extension up front (via `_gltfUsedExtensions`, reading the glTF JSON
  directly rather than trusting GLTFLoader to report it) and routes those
  files to `_parseGltfGaussianSplatting` instead, bypassing GLTFLoader
  entirely for them.
- Reads the glTF JSON + binary buffer (the GLB `BIN` chunk, or a `data:` URI
  for a self-contained plain `.gltf`) directly: resolves accessors
  (including interleaved ones via `byteStride`, and every documented
  component type — `float32`/`snorm8`/`snorm16`/`uint8`/`unorm8`/`uint16`/
  `unorm16` with correct normalization) without going through GLTFLoader's
  own parsing, then builds true per-splat Gaussians the same way as `.sog`/
  3DGS-`.ply` (`SplatRenderer`). Degree-1/2 spherical harmonics are decoded
  when present (same cap as `.sog`/`.ply`, see `SplatRenderer`); degree 3 is
  not read.
- Unlike `.sog`/`.ply`, no axis-flip/chirality correction is applied: the
  glTF coordinate system already matches three.js's.
- The containing glTF node's world transform (walked from the scene's node
  hierarchy, supporting both `matrix` and `translation`/`rotation`/`scale`
  node properties) is applied via the resulting mesh's own
  `position`/`quaternion`/`scale` — not baked into the splat data — so the
  existing shader's `modelMatrix`-based covariance/lighting math (already
  correct for every other mesh type in this viewer) handles it unchanged.
- A primitive declaring `colorSpace: "lin_rec709_display"` (linear-light,
  rather than the default/common `"srgb_rec709_display"`) gets a standard
  sRGB OETF applied in the fragment shader before output, since this
  viewer's custom `ShaderMaterial` bypasses three.js's own output-encoding
  pipeline.
- If `_parseGltfGaussianSplatting` finds the extension declared but can't
  actually decode any primitive (missing/unreadable accessors), it falls
  back to the normal GLTFLoader mesh path as a last resort rather than
  giving up outright.

## Annotations & BCF

Every annotation is a **viewpoint tied to a Work Package**, mirroring the BCF
2.1 structure used by OpenProject's BIM module:

| Plugin | BCF equivalent |
|---|---|
| `SpatialAnnotation` | `Bim::Bcf::Viewpoint` (camera, lines, clipping planes, snapshot) |
| `SpatialAnnotation#work_package` | `Bim::Bcf::Issue#work_package` (the topic) |
| `SpatialAnnotation#json_viewpoint` | BCF 2.1 viewpoint JSON (built in `to_bcf_viewpoint_json`) |
| snapshot attachment (`description: "snapshot"`) | BCF viewpoint snapshot |

Placing a pin / drawing / measuring opens an inline **"New Work Package"
panel beside the viewer** (like the BCF split view), not a modal overlay:
subject, type, priority, assignee, description — or "Link existing" to pick
a Work Package. The 3D viewport stays interactive on the left.

Flow on save (`SpatialAnnotationsController#create`):

1. A Work Package is resolved — the one selected, or a new one created via
   `WorkPackages::CreateService` from the panel fields. `work_package` is
   mandatory.
2. The canvas snapshot (data URI) is stored as a real attachment.
3. `json_viewpoint` is computed from the camera + drawing geometry, converting
   the viewer's Y-up coordinates to the BCF/IFC Z-up convention.
4. `SpatialViewer::SyncAnnotationBcfJob` mirrors the annotation into
   `Bim::Bcf::Issue` + `Bim::Bcf::Viewpoint` (keyed by `viewpoint_uuid`),
   running as the system user. The snapshot is copied to the BCF viewpoint.

Result: the annotation shows up in the **"BCF" section of the Work Package
page** (thumbnail gallery), and in the plugin viewer's side panel (thumbnail +
WP link; click restores the camera).

### Requirements / degradation

- The `Bim::Bcf` models are always present (bundled module), but the BCF group
  only appears on the WP page when the project has the **BIM module enabled**
  and the role has `view_linked_issues`.
- Without BIM, the mirror step is a no-op and annotations live only in the
  plugin viewer's panel (still linked to the WP, reachable via its link).

### Known limits

- Component selection/coloring (`ifc_guid`) is not populated — our OBJ/PLY
  models have no IFC GUIDs, and IFC is served as converted GLB.
- Clicking a viewpoint thumbnail *on the WP page* targets OpenProject's own IFC
  viewer, not this plugin's viewer. Camera restore across the two viewers is
  best-effort (axis conventions differ).
- BCF comments ↔ Work Package journal are not wired yet (follow-up).

## IFC

IFC is not rendered client-side: it is **converted to GLB on the server** and
the viewer loads the GLB (which already works).

Pipeline:

1. On upload (`create`/`update`) or first open, `SpatialModel#enqueue_conversion`
   schedules `SpatialViewer::ConvertIfcJob`.
2. The job runs `SpatialViewer::IfcConverter`:
   `IfcConvert -q -y --no-progress --center-model <in.ifc> <out.glb>`.
3. The GLB is cached at
   `<attachments_storage_path>/spatial_viewer/<model_id>/model.glb`.
4. Status (`pending` / `processing` / `completed` / `error` + message) is stored
   in `spatial_models.settings["conversion"]` and exposed by `api_data` in the
   `conversion` field. Until it is `completed`, `model_file` returns JSON and the
   viewer polls, showing "Converting IFC on the server".
5. The cache is invalidated automatically when the attachment changes
   (`conversion.attachment_id`) and removed when the model is deleted.

### Requirements / configuration

- The `IfcConvert` binary (IfcOpenShell). Looked up in: `IFCCONVERT_BIN`,
  `<Rails.root>/bin/IfcConvert`, `/opt/openproject/bin/IfcConvert`, `$PATH`.
  The OpenProject BIM module already installs it at `bin/IfcConvert`.
- `attachment_max_size`: for this module the limit is **bypassed**
  (`AttachmentPatch#internal_container?`), so large IFC files still attach.
  Watch disk space.
- Environment variables:
  - `SPATIAL_VIEWER_MAX_IFC_MB` (default `300`) — above this the conversion is
    rejected with a message pointing to the BIM module.
  - `SPATIAL_VIEWER_CONVERT_TIMEOUT` (default `1800` seconds).

### Large models

- `gltf_worker.js` parses GLB/GLTF in a **Web Worker** (no main-thread freeze),
  transferring de-interleaved geometry back to the viewer. Textured / Draco /
  meshopt models fall back to a main-thread `GLTFLoader.parse()`.
- The download is buffered through a `Blob` and the `ArrayBuffer` is transferred
  to the worker, so it is not held on the main-thread heap during parsing.
- A `HEAD` request checks the size first: above `data-max-model-mb` (default
  250) the viewer asks for confirmation before downloading.
- Above `data-heavy-model-mb` (default 40), or >4M triangles, "heavy mode"
  turns off shadows and caps `pixelRatio` at 1.
- Still not solved: no Draco/meshopt/KTX2 decoders (compressed GLB fails with a
  clear error), no BVH raycast, no LOD. Very large models (multi-hundred-MB
  Revit exports) are still better served by the BIM module's XKT/xeokit viewer.
- `IfcConvert` may log `Triangulation missing for face` on problematic geometry:
  these are warnings, conversion continues.
- `vendor/web-ifc*.js` and `vendor/IFCLoader*.js` are currently unused (kept for
  a possible future client-side path).

## History
